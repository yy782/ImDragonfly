# 多分片事务：VLL 轻量级事务模型

> **参考论文**：[VLL: A Lock Manager Redesign for Main Memory Database Systems](https://www.cs.umd.edu/~abadi/papers/vldbj-vll.pdf) — Ren, Thomson, Abadi, VLDB Journal, 2015
> **设计参考**：DragonflyDB
> **本文档讲"为什么这样设计"**：动机、权衡、收益。实现细节见 `src/facade/transaction.*`、`src/server/engine_shard.*` 等。

---

## 0. 结论先行

多分片事务要解决三个问题，VLL 各给一个回答：

1. **锁管理太贵** → 锁状态退化为每个 Key 上的两个原子计数器，锁表、等待队列、死锁检测图全部去掉
2. **死锁难缠** → 事务按单调递增 ID（时间戳序）获取锁，等待图必然无环——死锁在结构上被消除，连检测都不需要
3. **跨分片协调复杂** → 每核一分片（Thread-per-Shard），协调只在分片边界发生，用"意图 + 队列"两阶段非阻塞调度完成

一句话：**用时间戳序换取"无死锁"，用计数器换取"无锁表"，用队列换取"无等待图"**。

---

## 1. 基线问题：常规锁管理器为什么是瓶颈

### 难处

数据库从磁盘走向内存后，瓶颈迁移了。磁盘时代，一次 IO 毫秒级，锁管理的微秒级开销可以摊薄在 IO 等待里，无人在意。内存时代每个操作微秒级，锁管理的相对成本急剧放大——VLL 论文的核心观察正是：**锁管理取代磁盘 IO，成为内存数据库的吞吐瓶颈**。

传统 2PL 锁管理器由三件套组成，每一件都在拖后腿：

| 组件 | 成本 |
|------|------|
| 锁表（lock table） | 哈希表访问 + 锁节点分配；它是全局共享结构，本身就是热点 |
| 等待队列 | 每个锁挂一个等待者列表，需要额外的链表节点和指针维护 |
| 死锁检测 | 周期性构建/遍历等待图，最坏 O(事务数 × 边数) |

### 决策方向

不是优化这三件套，而是**问它们是否必要**。VLL 的答案是：锁状态不需要"谁在等"的信息（那是队列的职责），只需要"现在能不能拿"的信息——于是锁可以退化为计数器；而"谁在等"交给按时间戳排序的事务队列，等待图天然无环，死锁检测整个消失。

## 2. Thread-per-Shard：为什么"无锁"成为可能

### 架构前提

```
┌──────────────────────────────────────────────────────────────┐
│                   ShardPool                                   │
│  Thread 0         Thread 1         Thread 2         Thread 3 │
│  ┌─────────┐      ┌─────────┐      ┌─────────┐      ┌────────┐│
│  │ Shard 0 │      │ Shard 1 │      │ Shard 2 │      │Shard 3 ││
│  │ DbSlice │      │ DbSlice │      │ DbSlice │      │DbSlice ││
│  │ TxQueue │      │ TxQueue │      │ TxQueue │      │TxQueue ││
│  │EventLoop│      │EventLoop│      │EventLoop│      │EventLp ││
│  └─────────┘      └─────────┘      └─────────┘      └────────┘│
└──────────────────────────────────────────────────────────────┘
         ↑                ↑                ↑                ↑
         │   ShardId = Hash(key) % shard_count（确定性映射）    │
```

### 难处

Key 被哈希到固定分片。单 Key 命令只在一个分片内执行，天然线程私有、无需协调；但多 Key 命令（`DEL k1 k2 k3`、`MGET ...`）会横跨多个分片——**冲突只可能发生在分片边界**。

### 决策

- 分片内数据线程私有：普通数据结构不需要任何锁
- 跨分片时，每个参与分片上做三件事：拿锁（计数器自增）→ 入队（时间戳序）→ 就绪后执行
- 单分片事务走直通路径（不调度、不排队），多分片事务才付出协调成本

### 收益 / 代价

锁的粒度天然与数据布局一致（每分片一个队列），无全局锁表争用；代价是事务的并发性受分片数上限约束——但这也是"无共享"架构的固有特征。

## 3. 死锁：为什么可以根本性消除

### 难处

2PL 下锁的获取顺序是"事件驱动"的——谁先执行到访问语句谁先拿锁，与事务先后无关。这种无序性导致等待图可能出现环（T1 等 T2 的锁、T2 又等 T1 的锁），于是必须引入死锁检测或超时回滚，成本高昂且行为不可预测。

### 决策：给事务一个"年龄"

每个事务被分配一个单调递增的 ID（txid）。关键约束是：**冲突时，年轻的（ID 大）事务等待年长的（ID 小）事务**——锁请求按事务的"出生顺序"排序。

### 论证：等待图必然无环

等待图中的每条边"T_young 等待 T_old"，都严格从 ID 大的指向 ID 小的方向。沿边前进，事务 ID 严格递减，不可能回到起点。因此等待图是 DAG：

```
等待图中每条边：  T(younger) →waiting on→ T(older)
边方向 = txid 严格递减 → 不存在环 → 无死锁
```

### 推论

- 队列头事务（全分片最老）一定可以完成，因为所有冲突者都在它后面等待
- 不需要死锁检测，不需要等待图，不需要超时兜底
- "旧事务被新事务饿死"成为不可能：新事务要么排队，要么（更年轻的事务抢在前面）被取消重试

### 代价

txid 的分配与比较需要一个全局递增源；分片间需要同步"谁先谁后"的信息。本项目用分片队列 + 入队时 `txid` 比较实现，把代价限制在协调路径上。

## 4. 锁状态：两个原子计数器，为什么够用

### 难处

传统锁表要为每个锁保存：节点、持有者列表、等待者列表、模式……一次加锁可能要哈希查找 + 链表操作。而内存数据库每个操作本身只有微秒级，这些簿记占比惊人。

### 决策：把"锁"压缩成两个数

```cpp
// detail/intent_lock.hpp
class IntentLock {
 public:
  enum Mode { SHARED = 0, EXCLUSIVE = 1 };

  bool Acquire(Mode m) {
    ++cnt_[m];
    if (cnt_[1 ^ int(m)]) return false;           // 有相反类型锁存在
    return m == SHARED || cnt_[EXCLUSIVE] == 1;   // 排他锁要求只有自己
  }

  bool IsContended() const {
    return (cnt_[EXCLUSIVE] > 1) ||               // 多个排他竞争者
           (cnt_[EXCLUSIVE] == 1 && cnt_[SHARED] > 0); // 读写冲突
  }

 private:
  unsigned cnt_[2] = {0, 0};   // [共享锁计数, 排他锁计数]
};
```

获取规则：

```
Acquire(SHARED):    cnt_[EXCLUSIVE] == 0                    → 成功
Acquire(EXCLUSIVE): cnt_[EXCLUSIVE] == 1 && cnt_[SHARED] == 0 → 成功
```

### 为什么两个数就够

锁只回答一个问题：**"现在有没有人和我冲突？"** 至于"冲突的人是谁、排第几位、什么时候轮到"——那是事务队列的职责（§7），不是锁的职责。把"谁在等"从锁里剥离出去，锁就退化为一个计数器，加解锁只是原子自增/自减。

### 一个关键细节：失败不释放

`DbSlice::Acquire` 遍历一个事务的所有 Key 时，若某个 Key 检查出争用，**先前已自增的计数器不撤销**。这不是 bug，而是刻意的——保留的计数即"意图标记"：后续事务检查到争用，就知道前面有事务排着队，乖乖入队而不是硬闯。锁的"意图"比锁的"持有"更廉价、也更持久。

### 收益 / 代价

加解锁是 fetch-add 级别；代价是锁本身不再区分"持有者"，任何冲突都只能去排队——所以需要 §7 的队列来兜底调度语义。

## 5. 事务切分：一个多 Key 命令怎么拆到分片

### 难处

`DEL key1 key2 key3` 三个 Key 可能落在不同分片。命令层拿到的是扁平参数列表，调度层需要知道：每个 Key 属于哪个分片、每个分片上要锁哪几个 Key、参数怎么切分给各分片执行。

### 决策：InitByArgs → 按分片分组 → 每分片一份状态

```
DEL key1 key2 key3
  → DetermineKeys: {start=1, end=4, step=1}   // 哪些参数是 Key
  → BuildShardIndex: 按 ShardId 分组
       Shard 0: {key1, key3}  → 参数区间 [1,2] + [3,4]
       Shard 2: {key2}        → 参数区间 [1,2]
  → InitShardData: 每个活跃分片一份 PerShardData
```

每个参与分片的独立状态（一个事务一份）：

```cpp
struct PerShardData {
  uint16_t local_mask;       // ACTIVE | KEYLOCK_ACQUIRED | OUT_OF_ORDER | ...
  int16_t slice_start;       // 该分片的参数区间起点
  int16_t slice_count;       // 参数区间数量
  uint32_t fp_start;         // 锁指纹起点（kv_fp_ 数组内）
  uint32_t fp_count;         // 该分片要加的锁数量
  TxQueue::Iterator pq_pos;  // 在 TxQueue 中的位置（kEnd = 不在队中）
  atomic_bool is_armed;      // 是否已就绪等待执行
};
```

### 关键优化

- **单 Key**：直接填一个 `PerShardData`，`unique_shard_cnt_ = 1`，后续走直通路径
- **多 Key 撞同一分片**：分组后 `unique_shard_cnt_` 仍是 1，自动退回单分片路径——调度模型统一，性能不亏

### 收益

"事务涉及几个分片"被压缩成一个数 `unique_shard_cnt_`，调度逻辑只有一条分支；每个分片的数据（参数、锁、队列位置、就绪标志）全部就地预置，执行阶段不再做任何解析。

## 6. 调度：两阶段 + 乐观路径

### 难处

多分片事务必须在所有参与分片上"都拿到锁、都排好队"才能执行。若逐分片阻塞等待，先完成的分片会空转，还容易引入新的等待顺序依赖；若盲目并发，又可能部分成功部分失败。

### 决策：Schedule → Dispatch 两阶段，全程非阻塞

```
阶段一 Schedule（协调线程发起）：
  每个参与分片：Acquire 意图锁 → 失败则入队 → 记录队列位置
  任一失败 → 取消已入队的 → 整体重试（while(true)）

阶段二 Dispatch（协调线程触发）：
  武装 is_armed → 各分片 PollExecution → 队头就绪 → 出队执行
```

两阶段被 barrier（`RunBlockingBarrier`）同步：协调者等所有分片完成阶段一，再统一进入阶段二。**没有线程在等待期间阻塞自旋**，等待的只是"所有分片都走到同一里程碑"。

### 乐观路径：大多数事务不排队

阶段一里若锁全部拿到且无争用（`IsContended == false`），事务标记 `OPTIMISTIC_EXECUTION`，**直接在调度回调里执行，不进队列**——这是无争用负载的默认路径，排队成本为零。只有真正撞上冲突的事务才入队。

### 插队检测：防止优先级反转

入队前检查"我的 txid 是否比队尾事务新"。若已有更年轻的事务排在我后面（说明我被插队了）且我还没拿到锁，则**放弃重试**——保证队列始终按 txid 有序，维护 §3 的无环等待性质。

### 收益 / 代价

无争用时只付出"两个原子自增 + 一个 barrier"；有争用才付队列成本。代价是重试机制：极端争用下事务可能反复取消重排（由 SCA 缓解，见 §10）。

## 7. TxQueue：无死锁的等待队列

### 难处

"谁在等"的信息必须有个地方放。朴素实现（每锁一个等待链表）回到了锁表时代；用全局队列则引入跨分片争用。

### 决策：每分片一个队列 + 节点池

```cpp
class TxQueue {
  // 双向链表，节点池复用（Pop 的节点进 free_head_ 供后续 Push 复用）
  vector<Node> vec_;   // 节点池
  uint32_t head_, tail_, free_head_;
};
```

- 每分片一个 `TxQueue`，只被该分片线程访问，无需加锁
- `Push` 复用空闲节点：**入队出队零分配**
- 队列语义 = §3 的结论：**队头事务一定能完成**

### 就绪机制：武装与解除

入队 ≠ 立刻执行。协调者完成阶段一后，通过 `is_armed`（PerShardData 中的原子标志）"武装"事务；分片的 `PollExecution` 遍历队列，只执行已武装且排到队头的：`DisarmInShard` 检查 `is_armed` 并解除，返回就绪掩码。

```
队列状态:
  [T1(armed)] → [T2] → [T3] → ...
   头
PollExecution:
  T1 armed → 执行 → 出队 → 释放锁 → 通知
  T2 未 armed（其他分片还没就绪）→ 停止遍历，等下一次触发
```

### OUT_OF_ORDER：锁拿了就不用排队

阶段一拿到锁的事务标记 `OUT_OF_ORDER`。这样的分片在执行触发时**可以越过队列直接跑**——因为它的锁已经握在手里，与队列顺序无关（它在等的是"其他分片都就绪"，而不是"本分片的锁"）。只有真正没拿到锁的事务才严格按队列顺序执行。

### 收益 / 代价

O(1) 入队/出队、零分配、单线程内访问无锁；代价是队列顺序与锁获取顺序需要 §6 的插队检测来维护，否则 §3 的无死锁论证不成立。

## 8. 执行与释放：RunInShard

### 难处

执行完成 ≠ 事务完成：一个多分片事务要等**所有**参与分片都执行完才能恢复协调协程。用互斥锁保护"完成计数"会造成唤醒风暴和额外争用。

### 决策：barrier 计数，而非锁

```cpp
// RunInShard 执行序列：
RunCallback(shard)          // ① 执行该分片的命令逻辑（如 OpDel）
txq->Pop(sd.pq_pos)         // ② 出队（若在队中）
Release(mode, lock_args)    // ③ 释放 Key 锁（收尾阶段）
FinishHop()                 // ④ barrier 减一
ResumeIfNeed()              // ⑤ 归零 → 恢复协调协程
```

- 锁在**执行之后**才释放：释放即发布结果，后续事务读到的一定是已提交的可见状态
- 完成同步用 `RunBlockingBarrier` 计数：每个分片 `Dec()`，归零才恢复协程。等待方不持有任何锁，唤醒路径单一

### 收益 / 代价

无锁完成同步、无唤醒风暴；代价是"部分分片先做完、只能等"——这是两阶段屏障的固有特征，但等待发生在分片线程的空闲时段，不影响其他事务。

## 9. 权衡总览

| 设计点 | 难处 | 决策 | 收益 | 代价 |
|--------|------|------|------|------|
| 锁表 | 哈希/节点/热点 | 两个原子计数器 | 加解锁 = fetch-add | 锁不区分持有者 → 靠队列兜底 |
| 死锁检测 | 等待图 O(n·e) | 时间戳序获取锁 | 结构上无死锁 | txid 分配与比较 |
| 等待队列 | 每锁一链表 | 每分片一队列 + 节点池 | O(1)、零分配、无线程争用 | 队列序需插队检测维护 |
| 跨分片协调 | 阻塞等待低效 | 两阶段 barrier + 乐观路径 | 无争用零排队 | 极端争用下有重试 |
| 执行完成 | 锁保护计数 | barrier 计数 | 无唤醒风暴 | 分片需等待同步点 |

整体：无争用路径 ≈ 单分片速度；冲突才付出"排队 + 重试"成本。并发正确性由"时间戳序 + 意图锁 + 队列"三者共同保证。

## 10. 扩展：选择性争用分析（SCA）

> SCA 是 VLL 论文第 6 节提出的优化，本项目尚未实现——记录在此作为演进方向。

### 难处：热点 Key 把一切串行化

基础 VLL 下，100 个事务同时 `INCR counter`：全部自增计数器 → 全部检测到争用 → 全部入队 → 串行执行。吞吐跌到单线程水平。问题不在锁，而在于**调度对冷热 Key 一视同仁**——那些本可并行的事务被热点拖下水。

### 决策：区分冷热

- 每个 Key 维护争用计数，随冲突上报而递增、随时间窗口衰减
- 冷 Key → 乐观路径（零开销）；热 Key → 强制序列化轨道（提前排队）
- 跨冷热事务：先锁热侧、后锁冷侧，热点序确定事务执行序，无死锁性质不变

### 价值

冷负载零开销、热点定向管控、热度可衰减——SCA 不是替代 VLL，而是在其上加一层**自适应调度策略**。
